# Amalia: контракт сильного UI/UX для ИИ

> **Если ты — ИИ и создаёшь или редактируешь экран Amalia, сначала прочти этот файл целиком.**
> Результат должен выглядеть как продуманная часть приложения, а не как JSON-форма, отладочная панель или демонстрация всех доступных компонентов.

Начальная точка для передачи документации модели: [пакет автора и готовый prompt](AI_PLUGIN_AUTHORING.md).

Связанные документы: [фактический UI SDK](SDK_GUIDE_RU.md#14-sdk-интерфейсов-и-studio), [платформа UI](plugin-platform/06-UI-AND-VOICE.md), [полный пример](examples/beautiful-focus-ui.json).

## 1. Цель — не «красивее любой ценой»

Сильный экран одновременно:

1. за секунды объясняет, **что здесь можно сделать**;
2. показывает **самое важное первым**, а второстепенное — по запросу или ниже;
3. имеет один заметный смысловой центр и не более одного primary-действия;
4. помогает завершить задачу, понять результат и восстановиться после ошибки;
5. естественно живёт в стекле, свете и воздухе Amalia: без собственной темы, жёстких цветов и визуального шума.

«Больше стекла», «больше текста», «больше градиентов» и «больше анимации» сами по себе качество не повышают.

## 2. Обязательный порядок работы модели

### Шаг 1. Сформулируй UX до JSON

Коротко определи для себя:

- **Задача:** одно основное действие пользователя.
- **Герой:** одна главная информация или состояние, ради которой открывают экран.
- **Действие:** что должно произойти после нажатия; не выдумывай несуществующий provider.
- **Данные:** что реально известно, что приходит через `STATE`/`FORM`, что пока неизвестно.
- **Состояния:** что видно при загрузке, отсутствии данных, ошибке, запрете и конфликте.

Не проси пользователя выбирать «дизайн-систему»: она уже задана Amalia. Не заменяй его цель модным шаблоном.

### Шаг 2. Выбери композицию

Один из вариантов для экрана с главным состоянием (не шаблон для любой задачи):

```text
stack
├── hero                  только если нужен отдельный смысловой центр
├── grid                  2–4 важных показателя, только если они нужны
├── section               основной рабочий блок
│   ├── item / input      конкретный контент или ввод
│   └── primary           одно главное действие, если действие существует
└── section / text        вторичные детали, только если они помогают
```

Это **паттерн, а не чек-лист элементов**. Для простого экрана достаточно рабочего блока и действия. Hero необязателен: не добавляй его, если он повторяет заголовок экрана. Для формы герой может быть коротким, а рабочий блок начинаться сразу после него.

### Шаг 3. Собери реальный документ

- Используй только компоненты и свойства из таблиц ниже. Не выдумывай `style`, `color`, `padding`, `fontSize`, `background`, `gradient`, `elevation`, `onClick`, `visible` или CSS-подобные поля.
- Весь пользовательский текст хранится в `strings`; свойства `*Key` содержат **ключ**, не сам текст.
- Все использованные `labelKey`, `titleKey`, `*Key` и `confirmationKey` заполни во **всех девяти локалях**: `ru`, `en`, `ja`, `de`, `es`, `fr`, `zh`, `hi`, `ar`.
- Каждый узел имеет уникальный `id`; `children` содержат ID существующих узлов. Нет циклов и лишних недостижимых узлов.
- Документ должен пройти `UiDocuments.validate`. Preview — необходимая проверка, но не доказательство работы сетевых действий.
- Сохрани и собери пакет только после валидации. Не заявляй, что UI протестирован на устройстве, если видел только исходник или preview.

## 3. Компоненты: какие есть и когда их брать

### Композиция

| Компонент | Назначение | Свойства |
|---|---|---|
| `org.amalia.ui.stack` | Корень экрана: воздух между смысловыми блоками | нет; children |
| `org.amalia.ui.column` | Компактная последовательность внутри блока | нет; children |
| `org.amalia.ui.grid` | Метрики/равнозначные краткие карточки; на узком экране сам становится одной колонкой | `columns`: `2` или `3`; children |
| `org.amalia.ui.spacer` | Редкое дополнительное разделение смысловых частей | `size`: `xs`, `sm`, `md`, `lg`, `xl` |
| `org.amalia.ui.divider` | Разделение близких по смыслу частей | нет |

**Не оборачивай каждый текст в стекло.** Обычный `text` может существовать прямо в `column`/`stack`. Не строй длинные цепочки `column → glass → column → glass`.

### Смысловые блоки

| Компонент | Когда использовать | Свойства |
|---|---|---|
| `hero` | Один главный блок: польза, текущий статус или результат | `titleKey`, `subtitleKey`, `eyebrowKey`, `icon` |
| `section` | Тематическая группа с заголовком и содержимым | `titleKey`, `subtitleKey`, `elevated`; children |
| `item` | Строка сущности/настройки: название, пояснение, значение; с `actionId` становится нажимаемой | `titleKey`, `subtitleKey`, `valueKey`, `icon` |
| `metric` | Один значимый показатель, не декоративная статистика | `titleKey`, `valueKey`, `captionKey`, `accent`; опционально `value` |
| `progress` | Реальный прогресс от `0.0` до `1.0`, значения ограничиваются renderer | `titleKey`, `captionKey`; обязателен `value` |
| `badge` | Короткий статус; точка + текст, состояние не зависит только от цвета | `tone`: `neutral`, `accent`, `success`, `warning`, `error` |

Для hero/section/item доступен `surface: auto|plain|glass` (подробнее в разделе 10).

`hero.titleKey` может заменяться общим `labelKey`. Для `item`, `metric` и `progress` аналогично: `titleKey` приоритетнее `labelKey`.

`metric.value` — это **binding**, а `valueKey` — запасной локализованный текст. Не путай их. Пример binding:

```json
"value": {"source": "STATE", "sourceId": "snapshot", "pointer": "/progress"}
```

Если данных для `metric`, `progress` или `badge` нет, не сочиняй значения. Используй честное пояснение или подходящее состояние.

### Базовый контент и действия

| Компонент | Назначение |
|---|---|
| `heading` | Небольшой заголовок без создания новой стеклянной поверхности |
| `text` | Основной текст; `labelKey` либо `value` |
| `primary` | Единственное главное действие экрана/рабочего блока |
| `action` | Вторичное действие |
| `input` | Поле с видимым `labelKey`; значение доступно через `FORM` |
| `glass` | Простая группа без заголовка; в большинстве случаев предпочти `section` |

Для `item` разрешены иконки `none` и все иконки ниже. Для `hero`: `auto_awesome`, `bolt`, `favorite`, `check`, `schedule`, `info`, `notification`, `play`, `search`, `mind`, `wave`, `settings`.

## 4. Визуальная иерархия Amalia

### Обязательно

- **Один hero максимум.** Не превращай каждую секцию в баннер.
- **Одна primary-кнопка.** Повторное действие, delete, cancel и навигация — `action`, не `primary`.
- **До трёх текстовых уровней в блоке:** заголовок → тело → подпись. Не копируй один и тот же текст в `title`, `subtitle` и `caption`.
- **Короткие заголовки, полезные подписи.** «Фокус» вместо «Ваш персональный менеджер фокус-сессий»; «25 минут без уведомлений» вместо «Значение параметра: 25».
- **Контент важнее декора.** Не добавляй метрики «0», бейджи «Готово» и progress `1.0` только для заполнения места.
- **Только системные цвета и типографика.** Renderer уже использует `MaterialTheme`, `GlassCard`, циркадную палитру и токены отступов. Документ не может и не должен их перекрашивать.
- **Длинный текст не прячь.** Не рассчитывай на фиксированную высоту узлов; дай контенту переноситься. Используй короткие `valueKey` в `item`, чтобы не спорить с заголовком.
- **Не используй эмодзи вместо иконок или статусов.**

### Запрещённые антипаттерны

- экран из одинаковых карточек «заголовок + длинный текст» без иерархии;
- wall of text: инструкция, описание и технические детали одновременно наверху;
- primary без `actionId`, неработающая кнопка «Начать» или действие с выдуманным API;
- JSON, request ID, provider ID, hash, stack trace как главный пользовательский контент;
- «Успешно», пока операция только accepted/отправлена;
- пустой экран без объяснения, спиннер без контекста, ошибка без пути восстановления;
- три primary-кнопки, сетка из десяти метрик, вложенные glass-карточки, случайные иконки у каждой строки;
- непереведённые строки, английские fallback-тексты во всех локалях, псевдоперевод через ID ключа.

## 5. UX состояний и взаимодействий

`UiPhase`: `LOADING`, `EMPTY`, `READY`, `ERROR`, `DENIED`, `CONFLICT`. Для экрана с данными определи в `states` осмысленные ветки, а не только `READY`.

- **LOADING:** структура будущего контента, не техническая простыня и не ложные значения. Пока источники загружаются, runtime показывает loading перед соответствующим состоянием.
- **EMPTY:** что отсутствует + почему + следующее реальное действие. «Пока нет сессий. Начните первую — она появится здесь» лучше, чем «Пусто».
- **ERROR:** человеческое объяснение и повтор/выход там, где такая операция существует. Никаких обещаний автоматического retry.
- **DENIED:** какая возможность недоступна и что пользователь может изменить; не показывай заблокированную кнопку как будто она сработает.
- **CONFLICT:** объясни, что данные изменились; предложи безопасное обновление, если оно поддержано provider.
- **Ввод:** label всегда видим; ошибка должна быть связана с конкретным полем. Не делай необратимую операцию без `confirmationKey`.
- **Нажатия:** интерактивные native components уже имеют минимум 48dp, spring-отклик и блокировку повторной отправки. Не создавай свою имитацию через несколько кнопок.
- **Операции:** `Accepted` означает «принято», не «выполнено». Не сообщай успех до связанного terminal результата.

LOADING/READY/ERROR/DENIED переключаются по доступности источников. EMPTY/CONFLICT не определяются автоматически из бизнес-данных; states задаёт только отображение. Пустой list отображает своё empty-состояние.

Состояния переключает host/runtime, **не строки документа и не сама модель после отправки действия**. Для пользовательского текста ошибки provider используй локализуемые сообщения операции; не помещай произвольный технический `fallback` в заголовок экрана.

## 6. Качественный пример композиции

Полный статический документ лежит в [`examples/beautiful-focus-ui.json`](examples/beautiful-focus-ui.json). Это отправная точка по **иерархии**, а не экран, который надо копировать в любой предметную область.

Это макет композиции, без sources и actions: он не включает фокус-режим, не отключает уведомления и не измеряет прогресс. Его error/empty-ветки иллюстрируют текст, а не подтверждают наличие сохранённых данных. Для рабочего сценария замени эти предположения фактическими состояниями provider.

Его структура:

```text
Фокус (title экрана)
└── hero: «Тишина для важного» + понятная польза
    ├── grid: «Сессия · 25 мин», «Режим · Без уведомлений»
    ├── section: «Сегодня»
    │   ├── item: намерение + пояснение
    │   └── item: понятное намерение и граница сессии
    └── состояния: loading/empty/error/denied/conflict с понятным следующим шагом
```

Перед собственным экраном удали из паттерна всё, что не нужно его задаче. Например, для заметок hero может объяснять коллекцию, `item` — представлять заметку, а `EMPTY` — предлагать создать первую; метрики здесь не нужны.

## 7. Обязательная самопроверка перед сдачей

Ответь «да» на каждый пункт; если «нет» — исправь документ, а не объясняй недостаток пользователю.

### Смысл
- [ ] Понятна одна главная задача экрана, и она видна до второстепенных деталей.
- [ ] Нет декоративных данных, повторов и компонентов «чтобы было красивее».
- [ ] Действия соответствуют реальным declarations/providers и честно описывают результат.

### Иерархия
- [ ] Не больше одного hero и одной primary; есть ясный визуальный центр.
- [ ] `section` группирует смысл, `item` показывает сущность, `metric` — только значимые числа.
- [ ] Нет матрёшки из стекла, перегруженной сетки и длинной простыни одинаковых карточек.
- [ ] На узком экране контент остаётся читаемым; важные действия не теряются.

### Состояния и доступность
- [ ] Есть необходимые loading/empty/error/denied/conflict-состояния, если экран работает с источниками.
- [ ] У интерактивных узлов есть понятная локализованная подпись; статус читается не только по цвету.
- [ ] Ошибка объясняет следующий шаг; пустое состояние ведёт к реальному действию.
- [ ] Ничто не выглядит выполненным раньше фактического результата.

### Контракт
- [ ] Все компоненты, свойства, enum-значения и bindings существуют в этом гайде и SDK.
- [ ] Все строки переведены в девять локалей; IDs и связи узлов корректны.
- [ ] `UiDocuments.validate` не сообщает ошибок; затем проверен preview.
- [ ] Отдельно указано, что реально проверено: валидация, preview, сборка, установка, устройство.

## 8. Короткий prompt-блок для модели

Когда нужно встроить правила в системный prompt, используй этот блок **и приложи ссылку/содержимое полного гайда**, а не полагайся на него одного:

```text
Ты проектируешь native Android UI для Amalia через декларативный UI JSON.
Сначала соблюди docs/AI_UI_UX_GUIDE_RU.md целиком. Не выдумывай компоненты,
свойства, providers или данные. Создавай продуктовый экран, не карточную демку:
одна задача → подходящая композиция → главный рабочий блок → не более одного primary.
Используй semantic components (hero/section/item/metric/grid/progress),
системное стекло, тему и типографику Amalia; никаких цветов и размеров в JSON.
Обязательны девять полных локалей, реальные bindings, полезные empty/error/loading/
denied/conflict там, где применимо, понятные labels и восстановление после ошибок.
Не заполняй экран фейковыми метриками и не объявляй accepted операцию успехом.
Перед сдачей пройди checklist гайда, UiDocuments.validate и preview; честно
перечисль непроверенное. Элегантность важнее количества элементов.
```


## 9. Списки, формы и контекст действий

`org.amalia.ui.list` принимает через `value` полный JSON-массив. Пагинация локальная: она не отправляет сетевые запросы и не поддерживает cursor. Ровно один child задаёт шаблон строки; `ITEM` внутри него выбирает текущую запись, `pointer` — её поле. Вложенный list получает свой ITEM для своих строк.

| Свойства list | Контракт |
|---|---|
| `pageSize` | Целое 1–50, default 6 |
| `previousKey`, `nextKey`, `summaryKey` | Обязательные локализованные ключи |
| `emptyTitleKey`, `emptyDescriptionKey` | Необязательное описание пустого списка |

В `summaryKey` допустимы `{from}`, `{to}`, `{total}`, `{page}`, `{pages}`. У `item` доступны `titleBinding`, `subtitleBinding`, `valueBinding`: это объекты UiBinding, а не текстовые ключи. Например, `{"source":"ITEM","pointer":"/name"}`. Текст по binding приоритетнее соответствующего `*Key`.

Действие строки может использовать `ITEM` в input, например `"amount":{"source":"ITEM","pointer":"/amount"}`. Host захватывает запись при нажатии, до confirmation; смена страницы не подменяет её. Такое действие нельзя вызывать узлом вне строки. Повторная отправка блокируется по actionId на весь список до подтверждения окончательного результата; accepted не означает успех.

### Контролы формы

| Компонент | Properties | Значение FORM |
|---|---|---|
| `toggle` | `titleKey`, `subtitleKey`, `icon` (включая `none`) | boolean |
| `slider` | `titleKey`, `subtitleKey`, `min`, `max`, `step`, `unitKey` | number |
| `choices` | `options`: 1–8 объектов `{value, labelKey}`; value — строка 1–128 символов | string |

Каждому контролу нужен `labelKey`. `value` задаёт начальное значение (LITERAL/STATE), отредактированное FORM имеет приоритет. Не задавай собственный value через FORM на самого себя. В action.input используй FORM с sourceId нужного контрола. Без начального value toggle = false, slider = min (default 0), choices не выбрано. Числа min/max — 0–1000000, max строго больше min, default max = 1. Необязательный step — 0.000001–1000000. `input` остаётся строковым.

Не помещай input/toggle/slider/choices внутрь list: отдельная форма на запись не реализована, валидатор это отклоняет. Размести редактор отдельно от списка.

### Сообщения

`notice`: `titleKey`, `messageKey`, `icon`, `tone` (`neutral`, `accent`, `success`, `warning`, `error`). `state`: `titleKey`, `descriptionKey`, `icon`. Оба без children; title может использовать labelKey. Для retry используй отдельный action с реальной операцией.

[Пример списка с действием](examples/paged-list-ui.json) содержит девять локалей и ITEM-binding. Его действие соответствует `advance` из `examples/open-contract`. Это стендовый контракт: пример требует подключения demo-provider `org.example.implementation.counter`, contract `org.example.counter.counter` v1 и прав вызывающего клиента. В штатном приложении этот provider не установлен. Сам JVM-пример использует доверенный host и отдельную caller identity; для UI host должен подключить provider и выдать права caller-у экрана. Не обещай работоспособность действия без этого подключения. Данные списка — явно заданные варианты приращения, не выдуманные результаты операции.


## 10. Композиция без карточек внутри карточек

`hero`, `section`, `item` принимают `surface`: `auto` (default), `plain`, `glass`.

- `auto`: самостоятельный блок получает стекло; внутри стеклянной section её содержимое остаётся без дополнительных поверхностей. Внутренние metric/progress/toggle/slider/choices также используют поверхность группы.
- `plain`: типографика и контент прямо на циркадном фоне, без рамки. Для hero это основной выбор, когда главный образ — свет и воздух приложения.
- `glass`: явная самостоятельная поверхность. Внутри уже стеклянной группы используй только с обоснованием.

`hero` без icon не рисует декоративную звёздочку. Eyebrow необязателен; не добавляй «Ваш помощник» над каждым названием. `section` со стеклом группирует строки item и разделяет их; не вставляй между такими item дополнительные divider. `choices` — один радиосписок с видимой подписью, не россыпь независимых коробок.

Grid выбирает число колонок по доступной ширине и системному масштабу текста. Не обещай строго две колонки на любом телефоне. Короткое значение item располагается сбоку; на узкой ширине или при крупном системном тексте переносится под основной текст.

### Выбирай композицию по задаче

| Задача | Композиция | Смысловой центр |
|---|---|---|
| Настроить режим | краткое пояснение → section с controls → одно действие сохранения | текущее редактируемое решение |
| Найти запись | heading → input → list → отдельное empty | содержимое коллекции, без рекламного hero |
| Управлять воспроизведением | hero plain с названием → progress → primary → list очереди | текущий трек и управление |
| Посмотреть результат | hero plain с выводом → section с деталями → action следующего шага | вывод, не декоративные числа |
| Пустая коллекция | state с объяснением → реальное действие создания | первое полезное действие |

Это эскизы иерархии. Поиск, сохранение, playback и создание требуют реального provider; list сам не фильтрует, controls сами не сохраняют. Не рисуй активное управление без реализации.

[Полный пример формы](examples/preferences-ui.json) показывает композицию и типизированные начальные значения без действия сохранения. Это честный preview, не готовая функция настроек. Для рабочего плагина добавь существующую операцию и FORM-bindings. [Пример списка с действием](examples/paged-list-ui.json) отдельно показывает связку ITEM → input операции.

### Самокритика перед JSON

1. Назови одну задачу и элемент, на который взгляд должен попасть первым.
2. Выбери одну композицию из таблицы или обоснуй свою. Не копируй focus-пример независимо от предметной области.
3. Удали hero, badge, metric, eyebrow и icon, если после удаления ничего полезного не теряется.
4. Проверь путь «открыл → понял → сделал → увидел результат → восстановился после ошибки». Для каждого шага укажи реальный механизм SDK.
5. Сократи текст до заголовка и одной полезной строки; длинное объяснение помести ниже рабочего блока.
6. После preview проверь узкий экран, крупный шрифт и арабский: переносы, порядок чтения, видимость кнопок. Валидация JSON не доказывает качество композиции.


## 11. Кнопки и адаптивные группы действий

`org.amalia.ui.button` — кнопка существующей дизайн-системы Амалии. Обязательны `labelKey` и `actionId`. Properties:

| Поле | Значения |
|---|---|
| `variant` | `secondary` (default), `primary`, `quiet`, `destructive` |
| `icon` | один из разрешённых UI icons, необязательно |
| `enabled` | boolean, default true; false блокирует нажатие |

Primary/destructive используют настоящий PrimaryButton, secondary — SecondaryButton, quiet — облегчённое текстовое действие. Pending блокирует повторные нажатия, у primary виден встроенный loading. Accepted остаётся принятым запросом; завершение приходит отдельно через host. `destructive` обязательно требует confirmationKey у действия. Цвет не заменяет понятную подпись «Удалить запись».

`org.amalia.ui.actions` — группа children без properties. На достаточной ширине до трёх равных колонок; на узком экране и с крупным шрифтом кнопки переносятся в меньшее число колонок. Не размещай здесь длинный контент и более одного главного действия. Порядок children — порядок чтения.

Старые `primary` и `action` остаются совместимыми. Для нового экрана предпочитай button с явным вариантом. Не используй disabled-кнопку как обещание отсутствующей функции: поясни причину через notice или убери действие.

Готовые композиции и инструкция адаптации: [библиотека шаблонов](UI_TEMPLATES_RU.md). Точные свойства компонентов также доступны в [машинном контракте](UI_COMPONENTS.json): проверяй имена и enum по нему, не угадывай API по картинке.
