# 03. Runtime, пакеты, обновления и исправления

Статус: проект. [Навигация](README.md).

> Срез 2026-11-04: В исходниках есть verifier/staging, resolver, ActivationJournal, coordinator, host installer API и ограниченный Android DEX loader; install UI, ABI/dependency integration и data migrations ещё нужны. Фактический статус и ограничения CI: [IMPLEMENTATION.md](IMPLEMENTATION.md).

## 1. Единица поставки

Пакет может содержать декларации, исполняемый код, схемы контрактов, клиентские метаданные, ресурсы, локализации и миграции. Наличие UI или кода не обязательно. Вложенный пакет не активируется автоматически только из-за присутствия в архиве.

Предлагаемый манифест описывает:

| Группа | Данные |
|---|---|
| Идентичность | ID, версия, издатель, подпись, digest содержимого |
| Совместимость | Версии bootstrap-протокола, требуемый runtime/ABI |
| Контракты | Предоставляемые и требуемые версии, features |
| Зависимости | Обязательные/необязательные, конфликтующие реализации |
| Вклады | Точки расширения и ссылки на декларации |
| Ресурсы | Файлы, локали, схемы UI, модели |
| Данные | Версия хранилища и миграции |
| Доступы | Запрашиваемые права с областью и объяснением |
| Замены | Целевой поставщик, диапазон версий, требуемая совместимость |

Это новое проектирование. Текущий `PluginManifest` не поддерживает весь этот набор.

## 2. Проверка до исполнения

Порядок: лимиты размера/числа файлов → безопасное чтение архива → синтаксис → целостность → идентичность издателя → совместимость → зависимости → план изменений → staging.

Нельзя исполнять entry point для того, чтобы понять, совместим ли пакет. Проверяется path traversal, дубли записей, ссылки за пределы пакета, чрезмерное распакованное содержимое и корректность ресурсов.

Digest из того же недоверенного каталога обеспечивает сверку содержимого, но не независимое доверие издателю. Подпись связывается с политикой издателей и историей ключей.

## 3. Режимы исполнения

### Декларации

Хост/установленный renderer интерпретирует проверенные описания. Встроенные выражения имеют ограниченный язык, лимиты и разрешённые операции. Нельзя прятать произвольный shell в поле «видимость кнопки».

### Доверенный in-process DEX

Высокая интеграция и доступ к Kotlin/Compose. Код работает с правами процесса. Узкий фасад удобен для совместимости, но не является security sandbox. Зависший native-вызов или повреждение процесса не гарантированно ловится Kotlin try/catch.

Нужны правила SDK/ABI, упаковки зависимостей и запрет дублирования host API в пакете. R8 и Compose compiler compatibility учитываются отдельно; wire-протокол сам по себе не решает бинарную совместимость composable.

### Отдельный процесс / companion

Изоляция зависит от модели Android и UID. Другой процесс под тем же UID не даёт отдельные файловые права автоматически. Изолированный процесс имеет ограничения доступа. Companion под отдельным UID позволяет отдельную модель разрешений, но требует IPC и установки приложения.

### Удалённый runtime

Контракт исполняется на ПК/сервере. Данные, аутентификация, состояние связи и отмена явные. Отключённый телефон не превращает удалённый процесс в завершённый.

### Будущие runtimes

Runtime-provider сам может быть расширением поверх bootstrap, если хост уже способен загрузить его и передать ресурсы. Новый native ABI или Android-компонент всё же может потребовать APK. В первом этапе не требуется внедрять одновременно WASM, JS и все языки.

## 4. Жизненный цикл

Предлагаемые состояния:

```text
DISCOVERED → VERIFIED → RESOLVED → STAGED → STARTING → ACTIVE
                                               ↓         ↓
                                           FAILED     DRAINING → STOPPED
```

Отдельно существуют DISABLED, INCOMPATIBLE, QUARANTINED. Они не смешиваются с отсутствием разрешения конкретной операции.

Каждая активация получает generation, scope, ресурсы и регистрации. Отключение отменяет scope, закрывает подписки, снимает вклады и освобождает ресурсы. Долгоживущая работа выполняется через управляемые задачи, а не detached GlobalScope.

У callback регистрации есть срок/диагностика. Внешние эффекты не должны запускаться при чтении metadata. Ошибка onStart не публикует полузарегистрированную реализацию как ACTIVE.

## 5. Resolver зависимостей

Разрешаются контракты, версии, выбранные поставщики и runtime. Результат — объяснимый activation plan. Если выбор неоднозначен, используется профиль/явное решение, а не порядок файлов в каталоге.

Жёсткий цикл обязательного старта отклоняется. Для взаимного обнаружения применяется двухфазная регистрация: опубликовать описания, затем активировать готовые связи. Необязательная зависимость отсутствует — функция деградирует согласно декларации.

Lockfile профиля фиксирует найденную конфигурацию. Появление новой версии в магазине не меняет исполняемое поведение незаметно.

## 6. Ресурсы и бюджеты

Учитываются число задач, вызовов, объём хранения и логов, сетевой трафик, расходы провайдеров, CPU-время где измеримо. Для in-process кода часть лимитов договорная: нельзя обещать жёсткую изоляцию памяти одного плагина в общем процессе.

Эксклюзивные ресурсы выдаются lease: микрофон, камера, выбранная роль голосовой сессии. При потере lease исполнитель прекращает использование. Правила приоритета явные; старый callback не освобождает lease нового владельца.

## 7. Транзакция обновления

1. Скачать и проверить новую версию отдельно от активной.
2. Разрешить зависимости, оценить затронутых потребителей и задачи.
3. Подготовить снимок данных/миграцию.
4. Завершить или остановить старые операции по политике.
5. Активировать новую generation и переключить выбранные bindings.
6. Проверить запуск и критические операции.
7. Зафиксировать рабочий профиль либо восстановить предыдущий.

Это не единая ACID-транзакция с удалёнными устройствами и Android. Для каждого перехода нужен recovery journal, чтобы после смерти процесса определить достигнутую фазу.

Миграция данных может быть необратимой. Откат версии кода требует совместимого снимка данных; нельзя обещать rollback после удаления всех резервных копий. Внешние эффекты обновление не отменяет.

## 8. Плагин как исправление бага

Поддерживается явная замена реализации контракта. Исправляющий пакет указывает целевую роль/поставщика, версии и миграцию. Пользователь видит, что заменяется.

Два патча одной роли требуют решения конфликта; молчаливое наложение запрещено. Для композиции middleware сам контракт определяет порядок и семантику. Универсальные runtime hooks в произвольные методы APK не являются основой платформы.

Замена логики агента, экрана или преобразования данных возможна, если они вынесены за публичную границу. Баг загрузчика до активации, неверный manifest и часть native/runtime ошибок требуют обновления APK.

## 9. Восстановление

Перед стартом пользовательских модулей хост отмечает попытку загрузки. Повторный ранний crash позволяет запустить известный рабочий профиль/минимальный режим. Сбой не всегда можно точно приписать одному пакету: журнал показывает последнюю фазу, а не выдуманную причину.

Аварийный экран позволяет:

- не активировать сторонние пакеты;
- отключить выбранный пакет;
- вернуть прошлый профиль и совместимые данные;
- экспортировать очищенную диагностику;
- удалить пакет без запуска его UI;
- повторить запуск после изменения конфигурации.

Ядро остаётся уязвимым для собственных ошибок; recovery не является абсолютной гарантией от любого повреждения устройства/данных.

## 10. Каталог и доставка

Каталог, UI магазина, рекомендации и поиск — заменяемые функции. Минимальный установщик и проверка пакета принадлежат хосту. Локальный импорт не требует обязательного единственного магазина.

Канал обновления, доверие издателю и разрешение автоматической установки настраиваются отдельно. Плагин-студия не получает право одобрить собственные новые привилегии.

Динамическая доставка кода может ограничиваться правилами выбранного канала распространения приложения. Требуется отдельная проверка актуальных правил перед публикацией; эта спецификация не объявляет соответствие магазину.

## 11. Диагностика

Каждый вызов связан с package/version, provider/generation, task/trace. Логи структурированы, ограничены по объёму, маскируют секреты. Нормальное отключение не отображается как необъяснимая ошибка.

Экран диагностики различает: пакет установлен, runtime доступен, вклад зарегистрирован, поставщик выбран, операция разрешена, задача работает. Эти статусы нельзя свести к одному зелёному тумблеру.

## 12. Приёмка

- Повреждённый архив не запускает код и не портит активную версию.
- Отключение снимает регистрации и закрывает управляемые подписки.
- Новая generation не принимает запоздалый результат старой.
- Несовместимая миграция блокирует активацию до изменения данных.
- Неудачный UI-плагин отключается из recovery.
- Исправленный поставщик заменяет встроенный без пересборки APK.
- Удалённый runtime теряет связь без ложного статуса COMPLETED.
- Независимый пакет не использует внутренние классы `:app`.

## 13. Открытые решения

Формат подписи и ротации ключей; политика разрешённых издателей; точная схема data snapshots; совместимость Compose-пакетов; поддерживаемые режимы dynamic code на целевых Android; алгоритм аварийного запуска. Решения закрепляются отдельными ADR при реализации.
