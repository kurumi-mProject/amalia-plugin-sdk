# 07. Полный каталог требований пользователя: сценарии, ветви и отказы

Статус: сценарии проверки проектируемой платформы. Это не обещание, что текущий код уже умеет выполнять их. [Навигация](README.md).

## 1. TV → подтверждение → ПК → исследование → отчёт

### Намерение

Попросить Амалию найти и открыть видео на TV. После проверки она сообщает результат и спрашивает, продолжать ли. После ответа пользователя задача снова проверяет TV; при успехе делегирует исследование рынка на ПК; сохраняет данные и выводы; по запросу или расписанию создаёт отчёт в отдельном экране.

### Граф процесса

```text
Создана цель
  → найти paired TV и совместимое видео-действие
  → запросить/выбрать параметры, если не хватает данных
  → выполнить открытие
  → наблюдать/проверить фактическое воспроизведение
  → сообщить результат, создать ожидание «продолжить?»
  → после ответа сверить текущий device state (не использовать старую проверку)
  → направить дочернюю исследовательскую задачу paired ПК
  → получить источники и временно помеченные observations
  → хранить версионированный dataset
  → по просьбе/расписанию построить report artifact + chart data
  → показать экран и явно отделить факты от мнения модели
```

### Ветки

- TV не обнаружен → запросить сопряжение/выбор устройства, не сканировать соседей скрытно.
- На TV нет нужного приложения/API → объяснить поддержку и предложить доступный путь; не считать открытым лишь потому, что отправлен intent.
- Видео неоднозначно → спросить название/ссылку; не угадывать опасный переход.
- Воспроизведение недоступно для наблюдения → обозначить «команда отправлена, playback не подтверждён».
- Пользователь отвечает «нет» → сохранить результат и завершить процесс без следующего делегирования.
- Повторная проверка показывает остановку/другое видео → спросить, возобновлять ли; старый успех не засчитывать.
- ПК выключен → процесс ждёт device availability либо пользовательского решения согласно настройке.
- Исследование частично завершилось → сохранить частичные источники и отмеченный coverage; не генерировать полный отчёт как исчерпывающий.
- Источник устарел/не доступен → показать дату наблюдения и uncertainty.
- Планировщик Android задержал запуск → показать фактическое время выполнения, не обещанное точное.

### Платформенные механизмы

Durable workflows, device capabilities, question/resume, proof/state snapshots, remote task envelopes, artifact store, scheduled triggers, chart renderer, uncertainty/provenance. Ни один не должен иметь специализацию «YouTube» или «рынок» в ядре.

### Критерий

После остановки процесса/сети задача восстанавливает стадию и последний подтверждённый факт. Ответ на вопрос привязывается к правильному task ID. Повтор команды не приводит к двойному запуску.

## 2. Генерация и редактура изображения

### Намерение

Пользователь просит рисунок, получает версию, указывает, что поменять, и продолжает итерации. Может выделить область, сравнить версии, принять результат или откатить.

### Ветки

- Нет сервиса генерации → объяснить отсутствие provider.
- Provider вернул только низкое качество/thumbnail → хранить реальные параметры и не выдавать его за исходник высокого разрешения.
- Правка всей картинки нежелательна → использовать область/mask, если provider умеет; если нет, предупредить.
- Ответ модели — несовместимый media → отвергнуть и оставить последнюю рабочую версию.
- Отключение плагина во время генерации → отменить или сохранить task status как unknown, проверив provider позже.
- Удаление исходника → спросить перед удалением зависимых версий.

### Модель

Материалы и производные версии, prompt/provenance, области, provider contract, preview/full-resolution streams, управление правами на исходники.

### Критерий

Каждая правка связывает входной artifact и выходную версию; принятую версию можно восстановить. UI и голос работают с одним selected artifact.

## 3. Замена голосовой системы

### Намерение

Пользователь отключает текущую стратегию слушания/VAD/STT и устанавливает иной целый voice session provider или заменяет только segmentation.

### Ветки

- Новый provider не умеет требуемую sampling rate → показать несовместимость до переключения.
- Микрофон занят → очередь/отказ, не второй recorder.
- Отзыв permission в процессе → остановить захват и сохранить явное состояние DENIED.
- Recognition provider теряет partial → final transcript всё ещё различим от пустой реплики.
- Обновление runtime во время слушания → stop/drain/activate/restart по политике.
- TTS и STT не совместимы по audio session → host output manager разрешает/объясняет.

### Критерий

Provider заменяем без редактирования AssistantScreen и оркестратора; состояние сессии, ошибки и interrupt одинаково наблюдаемы для клиентов.

## 4. Обнаружение и сеть экземпляров Амалии

### Намерение

Несколько доверенных экземпляров находят друг друга, сопрягаются с согласием владельца, обмениваются выбранными настройками и возможностями; пользователь определяет сотрудничество и роли.

### Ветки

- Обнаружен неизвестный телефон → только кандидат/информация, никаких команд и credential transfer.
- Сосед прислал похожий ID → проверка криптографической identity, а не display name/MAC.
- Код приглашения истёк/повторно использован → отказ.
- Отозванный peer отправляет запрос → reject до обращения к plugin provider.
- Обе стороны изменили одну настройку → конфликтная политика/выбор владельца, не «последняя дата победила» без контекста.
- Сеть разделилась → операции помечаются pending/unknown; reconcile по request ID и ревизии.
- Невозможно определить результат внешнего действия → запрос состояния; нельзя слепо повторить.
- Peer имеет старую версию контракта → negotiate/adapter или недоступность.
- Устройство не имеет фонового режима/доступа → честно показать ограничение.

### Критерий

Discovery никогда не означает доверие. Секреты и системные права не копируются при общем профиле. Операция адресуется парному устройству и имеет проверяемый trace.

## 5. Создание плагина самой Амалией

### Намерение

Пользователь описывает функцию. Агент создаёт проект, документы контрактов, код/schema, предлагает доступы, тестирует в build runtime, показывает diff/ошибки и preview. Пользователь одобряет установку/замену.

### Ветки

- Плагин только декларативный → validate/preview без compiler.
- Требует неизвестный Android permission → честно пометить как APK-level blocker, не обходить.
- Сборка упала → compiler diagnostics возвращаются как artifact; агент исправляет ограниченное число итераций.
- Сборщик недоступен → проект сохраняется, показывается очередь/пауза.
- Ошибка подписи/издателя → не активировать.
- Новый пакет конфликтует с поставщиком → показать diff activation plan и спросить выбор.
- Скомпилированный DEX падает при старте → recovery не запускает его далее и предлагает откат.
- Модель пытается выдать себе дополнительные права → отдельное согласование владельца.

### Критерий

Созданный пакет не импортирует app internals, имеет воспроизводимый build record, гранты и rollback reference. Неуспех не портит установленную версию.

## 6. Произвольный код и серверные проекты

### Намерение

Работать с выбранным проектом, анализировать/создавать файлы, запускать проверки, читать ошибки и повторять исправления; локально или на разрешённом сервере.

### Ветки

- Scope вне выбранного project root → отклонить до команды.
- Команда разрушительная → показать план/дифф и запросить нужное подтверждение по политике.
- SSH host key изменился → остановить и перепроверить fingerprint.
- SSH оборвался во время deploy → проверить реальное состояние, не повторять вслепую.
- Лог содержит секреты → редактировать при сохранении/передаче модели.
- Тест успешен, продуктовый эффект не проверен → сообщить это отдельно.
- Серверная команда всё ещё работает после disconnect → отдельный remote job ID и отмена.

### Критерий

Каждая операция имеет рабочую область, исполнителя, результат и пределы; незнакомый бинарник не запускается автоматически только потому, что его создала модель.

## 7. Файлы, камера, уроки и предметные инструменты

Пользователь может попросить найти файл в выданных document trees, создать новый документ, переименовать или вернуть материал; попросить сфотографировать объект с разрешённой камеры и получить анализ; загрузить фото домашней работы и получить пошаговое объяснение; подключить строителя/архитектора, который работает со спецификациями и проверяемыми расчётами.

Ветки общего характера: URI grant истёк, файл поменялся, объект слишком большой, камеры нет, сеть недоступна, модель не уверена, предметные расчёты не проходят проверки. Плагин должен различать «предложение модели», «расчёт provider» и «подтверждённый результат». Фото может передаваться внешнему провайдеру только после понимания пользователем маршрута данных.

## 8. Замена багнутой функции

Тестируется замена одного поставщика новым plugin package; затем конфликт rollback; затем баг recovery/bootstrap, который плагин не способен решить и который правильно помечен как APK-level.

Признак успеха: заменяемые подсистемы не конструируются напрямую через `ServiceLocator` внутри потребителей. Исправление не применяет скрытые classloader hooks.

## 9. Безопасное взаимодействие и открытые действия

Все пути, где есть внешний эффект (платёж, заказ, удаление, публикация, изменение доступа, запуск сервера), должны иметь объявленную политику подтверждения и проверяемое состояние. Категория безопасности не может быть понижена подсказкой из manifest или текстом модели.

Для бытовой лампы автоматическое действие может быть заранее разрешено; для замка — отдельное решение владельца. Универсальность плагинов не отменяет различий риска.

## 10. Карта механизмов

| Направление | Контракты/механизмы |
|---|---|
| TV / ПК / дом | Device identity, remote dispatch, durable task, capability/provider registry |
| Рынок / отчёты | event stream, artifact versions, provenance, chart/UI contracts, scheduler |
| Картинки / музыка | media artifacts, provider discovery, shared state/actions, background adapters |
| Голос | replaceable voice-session contract и resource arbitration |
| Плагин-студия | project filesystem, build provider, diagnostics, preview, activation rollback |
| Файлы / камера / уроки | scoped resources, Android grants, multimodal transfer, provenance |
| Исправления | replaceable roles, state migration, generations, recovery profile |
| Непредусмотренное | plugin-defined contracts/extensions, adapters, alternate runtime providers |

## 11. Тестирование хаотичности

После набора обязательных сценариев участники предлагают новые случаи, не включённые в каталог. Спецификация успешна, если архитекторы не вводят host branch для предметной области: описывают пакет, его контракт и provider.

Новое фундаментальное системное требование фиксируется как gap. Нельзя объявлять его «идеей плагина», если без обновления протокола, runtime или APK оно действительно не работает.
