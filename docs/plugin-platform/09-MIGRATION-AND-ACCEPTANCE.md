# 09. Переход от текущего приложения и критерии приёмки

Статус: план миграции; реализация начата, фазы не считаются завершёнными автоматически. [Навигация](README.md).

Текущая отметка фаз A–I, CI и остаток работ: [IMPLEMENTATION.md](IMPLEMENTATION.md). Ниже сохранены исходная база и критерии цели.

## 1. Исходное состояние до начала миграции (2026-11-04)

- Gradle включает `:app`; модулей plugin API/runtime нет (`settings.gradle.kts`).
- Dynamic package — ZIP с `plugin.json`, опционально `classes.dex`; DEX загружает `DexClassLoader` (`plugin/dynamic/DynamicPluginLoader.kt`).
- `PluginContext` выдаёт Android Context и небольшой `HostServices` (`plugin/AmaliaPlugin.kt`).
- `ExtensionPoints.kt` содержит типизированные Contributor-контракты; они импортируют внутренние типы `data.ai`, `ui.theme`, `agent`, capability.
- `GroqEnginePlugin` объединяет Whisper, LLM и Fish Audio; tool groups получают функции через фабрики ServiceLocator.
- Навигационный NavHost ядра регистрирует экраны и extension screens; граф приложения частично знает о core routes.
- Сам кодовый DEX не является sandbox и имеет права процесса.
- Существующий plugin API документ отмечает будущий `:plugin-api`; это ещё не означает его фактическое наличие.

Это историческая база до миграции, а не перечень текущих модулей. Сейчас Gradle также включает `:platform:protocol` и `:platform:runtime`; legacy API продолжает работать. Актуальные факты и проверки см. в IMPLEMENTATION.md.

## 2. Фазы миграции

### Фаза A — заморозить текущие контракты и карту зависимостей

Инвентаризировать contributors, внутренние импорты, точки прямого создания функций, lifecycle, состояние, фоны Android, UI routes. У каждой функции определить: provider, данные, grants, наблюдаемый статус, error/recovery.

Результат: dependency map и реестр ролей, никакой массовой переписки до согласования границ.

### Фаза B — прототипировать корневой протокол

Проверить неизвестный контракт: независимый plugin A определяет его, plugin B предоставляет implementation, plugin C использует её. Ещё один provider заменить без перекомпиляции хоста. Протокол должен пройти schema validation, error, cancellation, version negotiation, event replay и artifact references.

Если все проверки требуют host type/branch, архитектуру дорабатывают до миграции продуктовых модулей.

### Фаза C — минимальный recovery и runtime ownership

Сначала обеспечить загрузку профиля, аварийный вход, disable/rollback и managed scopes. Затем переносить функциональность. Иначе каждая ошибка миграции может сделать приложение неоткрываемым.

### Фаза D — независимый SDK и внешний author workflow

Опубликовать минимальные client libs/codegen и шаблон независимого проекта. Удалить транзитивную зависимость SDK на `:app`. Проверить установку готового artifact без исходников Амалии.

### Фаза E — перенос встроенных функций

Переносить по ролям, не одним большим преобразованием: tool groups; storage; UI вкладки; голосовые стадии; агентный runtime; расписания. На каждом шаге сравнивать результат с прежним профилем и иметь обратимый binding.

Особо устранить прямое создание заменяемых классов потребителями. Не маскировать hardcode, обернув его API поверх той же единственной глобальной реализации.

### Фаза F — задачи, distributed providers, artifact model

Внедрить durable processes, вопросы и ответы, remote providers, file/resource handles, provenance, generation и unknown-outcome policy. Проверить reconnect и crash recovery до публичных заявлений о фоновой надёжности.

### Фаза G — декларативный UI и собственные ecosystem plugins

Renderer должен подключать компоненты/экраны расширениями, а не центральным перечнем доменных типов. Стандартный UI становится профилем. Установка неисправного UI не перекрывает recovery.

### Фаза H — plugin studio и bugfix replacement

Студия создаёт декларативный/кодовый пакет, вызывает выбранный build provider, сохраняет исходники/diagnostics, показывает grants и активирует staged build. Тестируется исправление provider, rollback, затем заранее известная невозможность починить bootstrap bug plugin-ом.

### Фаза I — пакет стресс-проверок и хаотичные идеи

Покрыть [07](07-USER-SCENARIOS.md), [08](08-PLUGIN-CATALOG.md), плюс идеи, отсутствующие в документах. Выбрать реальные устройства, API и сетевые разрывы. Каждый неуспешный сценарий повышает общий механизм только когда нужен общий механизм.

## 3. Приёмка цели 90–95%

Создать минимум 30 независимых задач из областей UI, медиаданных, генерации, обучения, творчества, серверов, локальных устройств, удалённой координации, replacement, workflow и новых придуманных областей. Не все 30 должны быть описаны разработчиком ядра заранее.

Для каждой задачи фиксировать:

- есть ли изменение app source/APK;
- есть ли изменение root protocol/базового SDK;
- можно ли доставить нужный runtime provider отдельно;
- внешние сервисы/оборудование и права;
- качество результата и доказательство выполнения;
- время интеграции и число host-specific веток;
- safety/recovery pass.

Показатели считаются отдельно для «без правки APK» и «без изменения базового SDK». Целевой диапазон 90–95% имеет смысл только с опубликованным знаменателем, набором кейсов и правилами классификации. Не считать фундаментальную Android-границу предметным провалом SDK, но не скрывать её из пользовательских ограничений.

## 4. Архитектурные ворота

### Gate 1 — настоящая граница

Независимый build; SDK не импортирует app implementation; API не выдаёт скрытый global service.

### Gate 2 — открытый предметный мир

Плагины публикуют неизвестный контракт, его provider, consumer и extension point без новых host interfaces.

### Gate 3 — заменяемость

Встроенный voice/session provider, agent strategy и UI заменяются по тому же механизму, что внешний пакет. Совместимая bugfix implementation активируется и откатывается.

### Gate 4 — жизненный цикл и восстановление

Отключение освобождает ресурсы; процесс переживает закрытие приложения в смысле durable state, но гарантии выполнения соответствуют Android; crash даёт рабочий recovery UI.

### Gate 5 — взаимодействие

Несколько UI/голос/automation clients используют одни действия и состояние; удалённый provider проходит handshake, pairing, revoke, reconnect и unknown effect.

### Gate 6 — авторская платформа

Плагин-студия создаёт собственную подсистему и второй пакет к ней, не меняя хост.

## 5. Нефункциональные проверки

- Никаких секретов в логах, промптах, каталогах и обычных export bundle.
- Размеры пакетов, schema depth, длительность вызова и event buffers ограничены.
- Событийные потоки не ломают Compose main thread.
- Выбор поставщика и grants отображаются пользователю.
- Удаление пакета имеет понятную политику сохранения данных и зависимых задач.
- RTL/локали/scale UI проходят базовую приёмку.
- Dynamic code policy проверяется для реального канала доставки.
- Статус «успешно» подтверждён provider fact, а не одной репликой модели.

## 6. Разделение рисков

| Риск | Мера |
|---|---|
| Универсальный runtime превращается в неконтролируемый произвольный код | Разделить режимы доверия, grants, runtime и ресурсы |
| Корневой протокол растёт бесконечно | Принимать только общие семантически доказанные примитивы; extension contracts остаются внешними |
| Один плагин блокирует весь процесс | Timeout/cancel где возможно, UI/recovery изоляция; in-process crash не обещать перехватить |
| Самопереписывание ломает продукт | Staging, diff, build report, явная активация, generation rollback |
| Случайные права из каталога | Installation != grants != activation; scoped consent |
| Плагины не понимают друг друга | Версии, schemas, adapters, capability negotiation |
| 90% превращается в лозунг | Публичный стресс-корпус и классификация host/SDK/Android blockers |

## 7. Что не делать

- Не переносить каждый файл в Gradle-модуль, называя это плагинностью.
- Не создавать отдельный обязательный Contributor на каждый пример из разговора.
- Не выдавать DEX за sandbox или универсальную live patch систему.
- Не обещать exactly-once для внешних действий.
- Не генерировать прямую Android UI/manifest permissions установкой произвольного пакета.
- Не объявлять новую архитектуру готовой только потому, что созданы документы или проект компилируется.

## 8. Итоговый критерий

Платформа принята, когда независимые авторы и сама Амалия способны создавать неизвестные предметные подсистемы, расширять их другими пакетами, заменять встроенные реализации и восстанавливать неудачные активации, а публичный набор хаотичных задач даёт целевое покрытие без скрытых host branches.

Успех проектирования, реализация, CI-сборка, policy review и device acceptance — отдельные статусы. Ни один не подразумевает следующий автоматически.
