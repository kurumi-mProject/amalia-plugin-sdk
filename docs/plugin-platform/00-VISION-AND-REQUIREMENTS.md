# 00. Видение, требования и границы

Статус: предлагаемая архитектура. [Навигация](README.md).

## 1. Что пользователь хочет получить

Не набор заранее придуманных интеграций и не SDK с новым Contributor под каждую следующую идею. Нужна программируемая платформа, на которой пользователи создают неизвестные разработчику функции, собственные подсистемы и расширения к этим подсистемам.

Примеры из обсуждения — стресс-проверки универсальности. Их нельзя превращать в список специальных веток ядра. Появление «биржи», «строителя» или «генератора музыки» в коде микроядра будет признаком неверной границы ответственности.

Конечный продукт: минимальный хост + стандартный комплект плагинов. При первой установке он сразу полезен, но почти каждую продуктовую часть можно отключить, обновить или заменить. Собственный UI и каждое его действие также принадлежат плагинам; независимый аварийный интерфейс остаётся доступен.

## 2. Нормативные требования

| ID | Требование |
|---|---|
| R01 | 90–95% репрезентативных новых идей должны реализовываться без изменений хоста |
| R02 | Новый предметный контракт определяет автор расширения, без выпуска базового SDK |
| R03 | Плагин может предоставить новую подсистему и её точки расширения |
| R04 | Встроенные и сторонние модули используют одинаковые публичные контракты |
| R05 | Ассистент, Мишка, голос, основные экраны и навигация заменяемы |
| R06 | Кнопки, голос и автоматизации вызывают одни операции над общим состоянием |
| R07 | Плагин имеет свои данные, настройки, ресурсы, локализации и миграции |
| R08 | Есть операции, потоки, события, передача больших материалов и отмена |
| R09 | Длительные процессы сохраняются, ожидают человека и продолжаются после ответа |
| R10 | Реализация контракта может жить на телефоне, ПК, сервере или другом устройстве |
| R11 | Можно создавать/собирать плагины средствами других плагинов |
| R12 | Замена совместимой реализации может исправить баг без пересборки APK |
| R13 | Существуют диагностика, аварийное отключение и восстановление запуска |
| R14 | Установка, активация, выбор поставщика и выдача прав — разные операции |
| R15 | Экраны собираются декларативно, сложные компоненты допускают код |
| R16 | Для нового вида runtime предусмотрен расширяемый путь, без обещания бесконечного ABI |
| R17 | Разработка возможна вне репозитория приложения, по опубликованным контрактам |
| R18 | Успех задачи подтверждается фактами исполнителя и проверкой эффекта |

## 3. Как трактовать 90–95%

Это продуктовая цель. Не существует измеримого процента «всех мыслимых идей». Приёмка использует открытый набор независимых сценариев из разных областей и новые сценарии, придуманные после стабилизации контрактов.

Считаем два показателя отдельно:

1. **Без изменения хоста:** сценарий реализован установкой пакетов и настройкой разрешённых подключений.
2. **Без изменения базового SDK:** новые предметные контракты и библиотеки поставлены независимо.

Внешний сервер, платный провайдер, дополнительное оборудование или companion не превращают невозможное локальное исполнение в локально реализованную функцию. Эти зависимости указываются явно. Для каждого сценария фиксируются требуемые ресурсы, изменения APK/SDK, качество и ограничения.

Не допускается искусственно улучшать процент, разбивая одну удобную функцию на сотню пунктов, исключая сложные случаи или меняя определение успеха после результата. Провал заносится в реестр архитектурных пробелов.

## 4. Все направления пользователя

- Локальные серверы и произвольные протоколы взаимодействия.
- Обнаружение своих устройств; телефон, Android TV, ПК, сервер; совместная работа.
- Дом как общая среда устройств, состояний и событий.
- Источники котировок, анализ, постоянное наблюдение и отчёты.
- Полноценный агент: вопросы, подтверждения, продолжение, проверка.
- Создание экранов по описанию, диаграммы, сохранённые представления.
- Цепочка TV → подтверждение → повторная проверка → ПК → исследование → отчёт.
- Генерация и последовательная правка изображений; ролеплей и дизайн.
- Полная замена слушания, VAD, STT и взаимодействия реплик.
- Сопряжение экземпляров, выборочный перенос настроек, совместные действия.
- Написание плагинов самой Амалией с отдельной студией.
- Полноценный медиаплеер, полностью управляемый ИИ.
- Файлы телефона: поиск, создание, выдача, переименование.
- Код: локальное/удалённое исполнение, ошибки, исправление и повторная проверка.
- Работа с разрешённым проектом на сервере пользователя.
- Замена неисправной реализации плагином.
- Рандомайзер, учебные задачи, помощник строителя/архитектора, генерация музыки.
- Снимок с камеры как вход для анализа и ответа.
- Новые направления, которых нет в этом списке; плагины с собственными экосистемами.

Подробные ветви и отказы: [07](07-USER-SCENARIOS.md). Каталог дополнительной проверки: [08](08-PLUGIN-CATALOG.md).

## 5. Что остаётся вне обещания

- Обход Android sandbox, приватных каталогов других приложений и системных ограничений.
- Получение невыданных прав или добавление новых manifest-компонентов обычным JSON-пакетом.
- Непрерывная работа телефона вопреки выгрузке процесса и ограничениям ОС.
- Автоматическое понимание произвольного неизвестного протокола без клиента/описания.
- Идеальная генерация кода, изображений, инженерных решений и торговых прогнозов.
- Универсальное горячее переписывание классов установленного APK.
- Настоящая изоляция DEX-кода лишь благодаря узкому Kotlin-интерфейсу.
- Исполнение любого бинарника на любом устройстве без подходящей среды.

## 6. Принцип против архитектуры из примеров

Для каждой новой идеи задаются вопросы:

1. Какие данные, действия, события, потоки и представления нужны?
2. Можно ли описать их новым контрактом плагина?
3. Есть ли требуемый исполнитель и доступ к системному ресурсу?
4. Если нет — это новая предметная функция или новый фундаментальный механизм?
5. Можно ли добавить поставщика/адаптер без изменения ядра?
6. Если необходимо изменение хоста, почему его нельзя избежать честно?

Ответ «нужен Contributor с названием новой области» по умолчанию отклоняется. Новый общий примитив вводится только после доказательства, что существующий протокол не выражает нужную семантику или не обеспечивает требуемые гарантии.

## 7. Разработка без преждевременного усложнения

Универсальность достигается расширяемыми границами, а не реализацией всех возможных языков, сетей и моделей в первом релизе. Начальный runtime может быть один, но контракт не должен считать его единственным навсегда. Начальный renderer может иметь небольшой каталог компонентов, но расширения должны уметь добавлять компоненты без редактирования большого when в приложении.

Не требуется переносить каждый маленький helper в отдельный Gradle-модуль. Граница пакета определяется жизненным циклом, независимым обновлением, ответственностью и публичным контрактом.

## 8. Что считается завершением проектирования

- Для каждого R01–R18 есть механизм и критерий приёмки.
- У каждого механизма понятны владелец, данные, сбои и ограничения.
- Отдельно отмечены открытые решения, а не спрятаны за словом «универсальный».
- Новый независимый автор способен определить неизвестную подсистему и расширить её вторым пакетом.
- Исправляющая реализация включается без обращения к внутренним классам.
- Отсутствие стандартного UI не блокирует управление пакетами и восстановление.
