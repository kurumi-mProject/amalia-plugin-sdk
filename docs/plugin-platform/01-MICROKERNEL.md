# 01. Микроядро и границы модулей

Статус: проект. [Навигация](README.md).

> Срез 2026-11-04: Локальные protocol/runtime и recovery уже добавлены, но продуктовые роли ещё не вынесены. Фактический статус и ограничения CI: [IMPLEMENTATION.md](IMPLEMENTATION.md).

## 1. Слои

```text
Android / оборудование / сеть
    ↓
Минимальный загрузчик и восстановление
    ↓
Реестр контрактов + диспетчер + права + жизненный цикл
    ↓
Исполнители и адаптеры системных ресурсов
    ↓
Профиль продукта из встроенных и установленных плагинов
    ↓
Подсистемы и экосистемы, определённые авторами плагинов
```

Стрелки показывают использование услуг нижнего слоя. Предметные реализации не импортируются ядром. Компоновка приложения остаётся в `core/di/ServiceLocator.kt`; предлагаемые модули не означают введение Hilt/Koin.

## 2. Несократимое ядро

| Ответственность | Почему остаётся |
|---|---|
| Начальная загрузка | Должен существовать путь до запуска любого плагина |
| Проверка пакета и идентичности | Нужно определить, какой код и какие декларации активируются |
| Минимальный протокол и маршрутизация | Участникам нужен общий язык обращения |
| Учёт контекста вызова и прав | Плагин не должен сам назначать доверенную личность отправителя |
| Владение жизненным циклом | Регистрация и завершение ресурсов должны иметь хозяина |
| Устойчивый журнал активаций | После сбоя нужен известный рабочий набор |
| Аварийный UI | Сломанный UI-плагин нельзя использовать для его собственного отключения |

Подсистемы хранения журнала и политик могут иметь заменяемые расширенные реализации, но ядру нужен работоспособный базовый путь. Нельзя строить бесконечную рекурсию «для загрузки загрузчика нужен другой плагин».

## 3. Что переходит в плагины

- Разговорный ассистент, выбранная персона, память и контекст.
- Агентный цикл Мишки, планировщики и стратегии проверки.
- Захват/обработка речи, VAD, KWS, STT, LLM и TTS в доступных системных границах.
- Экран ассистента, история, настройки функций, каталоги, главное меню и навигация продукта.
- Темы, виджеты, приветствия, визуализации, кнопки и команды.
- Инструменты устройства и интеграции приложений.
- Расписания и редакторы процессов поверх устойчивого исполнения.
- Плееры, генераторы, файловые браузеры, IDE и предметные модели.
- Магазин расширений и богатый UI установки; аварийный установщик остаётся.

Стандартная поставка включает рабочий профиль. «Пустой хост» означает независимость функций, а не обязательный пустой экран после установки.

## 4. Системные адаптеры

Android-компоненты, заранее объявленные в APK, принимают системные события и делегируют разрешённым обработчикам через платформу. Примеры: FGS, media session, Accessibility, activity result, уведомления, URI grants.

Плагин может реализовать новую предметную логику поверх этих адаптеров. Но новый тип Android Service, permission или manifest intent-filter не появляется автоматически из описания плагина. Нельзя заранее объявлять все мыслимые права только ради процента покрытия: это влияет на установку, доверие и распространение.

Адаптер обязан сообщать свои возможности и ограничения: версия ОС, доступность оборудования, фоновые ограничения, выданные права. Потребитель проверяет поддержку вместо предположения «все устройства одинаковы».

## 5. Предлагаемая физическая структура

Имена ниже — будущий вариант, не существующие Gradle-модули:

```text
:app                       Android entry points, сборка профиля
:platform:protocol         минимальные сообщения и схемы
:platform:runtime          пакеты, resolver, lifecycle, dispatch
:platform:android-host     системные адаптеры
:platform:recovery         независимый запуск и восстановление
:sdk:client                удобные обёртки над протоколом
:sdk:ui-compose            необязательные типизированные UI-обёртки
:plugins:*                 независимо выделяемые функции
```

Логическая граница фиксируется раньше полного физического разбиения. Экспорт SDK не должен тянуть `:app` транзитивно. Независимый проект плагина собирается без checkout исходников приложения.

## 6. Граф зависимостей

- Хост зависит от публичного протокола, не от конкретного агента или плеера.
- Клиентские библиотеки генерируются/пишутся по контрактам и могут обновляться независимо.
- Плагины зависят от контрактов, не от внутренних классов соседнего пакета.
- Предметная подсистема может предоставить свой SDK и точки расширения.
- Для обязательных циклических зависимостей активация отклоняется с объяснением; необязательные связи обнаруживаются после регистрации.
- Регистрация описывает возможности и не должна запускать внешние эффекты.

Вызов через реестр нужен на границах заменяемости. Внутренние вычисления модуля остаются обычными функциями без сериализации каждой строки.

## 7. Профили продукта

Профиль фиксирует версии пакетов, выбранных поставщиков и конфигурацию размещения UI. Возможны профиль «обычная Амалия», «музыкальная станция», «студия», пользовательская сборка.

Профиль не содержит открытые секреты. Установка профиля показывает отсутствующие зависимости и запрашиваемые доступы. Экспорт не копирует системные разрешения на другое устройство.

Отключение поставщика обязательной роли не должно молча включать другую реализацию с иными свойствами приватности. Хост показывает отсутствие роли либо использует заранее выбранный пользователем fallback.

## 8. Замена поведения и исправления

Замена выполняется на границе контракта. Потребитель держит логическую ссылку на выбранного поставщика, а не навсегда сохранённый экземпляр конкретного класса.

Перед переключением учитываются активные вызовы: drain, отмена или завершение на старой версии. Новые вызовы идут в новую generation. Поздний ответ старой generation не перезаписывает новое состояние.

Состояние переносится через явную миграцию. Если новая версия не понимает старый checkpoint, процесс остаётся на старом исполнителе, блокируется с объяснением или безопасно перезапускается по заданной политике.

Ошибки раннего загрузчика, ABI и manifest не обещается исправлять плагином. Для них нужен APK.

## 9. Производительность

- Управляющие сообщения отделены от больших бинарных потоков.
- Не сериализовать каждый PCM-сэмпл или каждый кадр UI как большой JSON.
- Контракты допускают согласованный быстрый локальный канал и переносимый внешний канал.
- Подписки активны по жизненному циклу потребителя; невидимый экран не держит ненужную анимацию.
- Общие ресурсы имеют арбитр: микрофон, аудиофокус, камера, длительные фоновые операции.
- Нет требования будить LLM при каждом событии датчика или изменении цены.

## 10. Критерии приёмки

1. Рабочий хост загружается без стандартного ассистента и показывает recovery.
2. Стандартная поставка полностью работоспособна с комплектом плагинов.
3. Внешний UI заменяет главный экран без изменений `AmaliaNavHost` под его предметную область.
4. Внешний агент использует только публичные контракты.
5. Замена одной функции не требует переноса остальных функций в тот же пакет.
6. Пакет не получает скрытый доступ только из-за нахождения в репозитории Амалии.
7. Код композиции не содержит switch по именам предметных сторонних плагинов.

## 11. Открытые решения

Точное минимальное множество host-native адаптеров; граница платформенного renderer и UI-плагина; стратегия публикации артефактов SDK; минимальная поддерживаемая версия wire-протокола; выделение удалённого bootstrap. Эти решения выбираются при реализации по стоимости, устройствам и критериям [09](09-MIGRATION-AND-ACCEPTANCE.md).
