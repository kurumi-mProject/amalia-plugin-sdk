# 06. UI, действия, экраны и голосовые роли

Статус: проект. [Навигация](README.md).

> Срез 2026-11-04: Главный экран, онбординг и справка исправлены в app; замена voice/UI ролей и декларативный renderer ещё не реализованы. Фактический статус и ограничения CI: [IMPLEMENTATION.md](IMPLEMENTATION.md).

## 1. Функция — не экран

Плагин публикует состояние и операции. Экран, голосовой агент, сценарий и другое устройство являются разными клиентами этого контракта.

```text
                         ┌→ декларативный экран / Compose
Плагин функции → API/state ├→ ИИ-инструмент и вопрос человеку
                         ├→ автоматизация
                         └→ удалённый клиент
```

Например, кнопка «следующий трек» и фраза «включи следующий» вызывают одну операцию. Авторитетное состояние очереди публикует плеер; UI не подделывает успешный результат своим локальным toggle.

## 2. UI-плагин и точки размещения

UI-плагин может предоставить самостоятельную навигационную структуру и вклады в именованные точки: главный экран, область быстрого действия, панель задачи, настройки, карточку результата, просмотр материала.

Хост предоставляет адаптер навигации, safe area, back, lifecycle и системные launchers. Плагин объявляет route/id, заголовок, иконку/ресурс, требования и точку размещения. Конфликт route обрабатывается проверкой до показа. UI не получает произвольный NavController, если public API даёт ограниченную навигацию.

Основной пользовательский UI может быть плагином. Recovery, первичная загрузка, разрешение критических конфликтов и отключение сломанного UI должны работать без него.

## 3. Декларативная схема

Предлагаемая схема описывает:

- структуру экранов и компонентов;
- идентификаторы данных и подписок на состояние;
- выражения отображения из ограниченного типизированного набора;
- действия при нажатии/вводе/подтверждении;
- загрузку, пустое состояние, запрет, конфликт, ошибку и retry;
- локализационные ключи, accessibility labels и семантику;
- пагинацию/виртуализацию длинных списков;
- валидацию форм и промежуточный статус операций.

Renderer должен быть расширяемым. Компонентный пакет регистрирует собственный renderer по контракту платформы; хост не содержит обязательный switch всех имён сторонних компонентов. Неподдерживаемый обязательный компонент отображается как incompatibility, а не исчезает молча.

Безопасные вычислимые expression имеют ограничения по времени, глубине и источникам. Нельзя запускать Kotlin/Java-код из обычного поля выражения.

## 4. Декларативное и кодовое UI

Декларативный UI даёт переносимость, превью, проверку и простую генерацию моделью. Compose-вклад позволяет сложные визуализации, анимацию и специализированные взаимодействия.

Compose-код остаётся кодом того же уровня доверия, что и DEX-плагин. Он должен соблюдать дизайн-систему Amalia: `AmaliaScreen`, `GradientBackground`, стеклянные поверхности, токены `colorScheme`/`typography`, lifecycle-aware StateFlow, accessibility и локализации во всех девяти локалях. Отдельный плагин-компонент может расширять библиотеку renderer, но не ломать базовый экран молча.

Авторская модель/ИИ может создать схему и предложить визуальный preview. Preview валидируется, сохраняется как версия; публикация нового экрана отделена от временной генерации документа.

## 5. Модель действия

Интерактивный элемент адресует публичную операцию контракта и объявляет:

- входные данные и их binding;
- политику повторного нажатия;
- отображение pending/result/error;
- возможность отмены;
- требуемое подтверждение;
- источник отображаемого состояния.

Нажатие не означает успешное выполнение. Loading и ошибка связаны с requestId. Повтор команды, эффект которой неизвестен, показывает уточняющее состояние, а не автоматически нажимает снова.

## 6. Сложные представления и диаграммы

Данные диаграммы имеют значения, единицы, временную зону, источник и временные метки. UI renderer знает тип диаграммы, шкалу и подписи, но не придумывает факты.

Текстовое мнение модели отделено от измеренных данных и помечается как интерпретация. Плагин может создать собственную визуализацию и отображать её вместе с исходными данными/периодом.

Создание временного отчёта и проектирование постоянного плагин-экрана — разные операции. Первая выдаёт версионированный artifact; вторая меняет проект/профиль после проверки.

## 7. Голос как заменяемая система

Не ограничиваться тремя движками STT/LLM/TTS. Определить отдельные роли:

- acquisition — получение источника звука;
- segmentation/VAD — границы речевых ходов;
- wake activation — условие запуска;
- recognition — partial/final transcript и confidence;
- turn manager — очереди, перебивание, отказ микрофона;
- orchestration/agent — решение и действия;
- speech generation — аудиовывод;
- output manager — очередь, ducking, stop и playback state.

Плагин может заменить одну роль либо whole voice-session provider. Whole-session provider сам владеет внутренним алгоритмом, но снаружи обязан соблюдать shared contract: lifecycle микрофона, ошибки, события реплик, отмену и наблюдаемые состояния.

Арбитр микрофона обязателен. Два слушателя не открывают AudioRecord параллельно. Поток sample/audio frame отделён от control messages. Поддерживаются backpressure, timestamp/sample-rate/channel metadata и остановка при отзыве доступа.

Семантика прерывания:

1. пользователь начинает говорить во время TTS;
2. voice provider сообщает interruption;
3. хост координирует остановку/ducking по выбранной политике;
4. результат незавершённого tool call помечается корректно;
5. новая реплика получает отдельный turn ID.

Перепроектирование голоса может выбрать другой протокол внутри одной версии если есть adapter, но не заставляет обновлять предметные плагины.

## 8. Экран ассистента и навигация

Стандартный профиль поставляет привычный экран и нижнюю панель. Другой UI-плагин может полностью поменять расположение, сохраняя общие контракты разговоров и задач. Навигационная модель может быть заменена отдельным router-provider при условии, что recovery сохраняет независимый вход.

Плагины регистрируют не только маршрут, но и действия, которыми маршрут открывается. Deep link проходит валидацию, проверяет доступ и не выполняет автоматически опасную операцию по одному URL.

## 9. Локализация, темы и доступность

SDK UI предоставляет host tokens, host string resources и разрешённые ресурсы плагина. Новый текст не хранится только в русской строке внутри Kotlin. Для стандартного пакета соблюдать значения ru default и девять локалей согласно проектным правилам.

Интерактивность имеет семантическое имя, роль, состояние, focus order и touch target >=48dp. Цвет не единственный канал состояния. Увеличенный текст, RTL и landscape включены в проверки.

Пользовательские цвета не обходят контраст-проверки общей темы. Изображение/диаграмма имеет текстовый эквивалент и описание.

## 10. UI генерации и плагин-студия

Студия показывает дерево проекта, diff, контрактные зависимости, доступы, результат компиляции, лог и preview. Созданный моделью экран сначала schema preview; Kotlin/Compose build исполняется выбранным build provider.

Установка версии проходит через runtime transaction из [03](03-RUNTIME-AND-PACKAGES.md). Студия не может сама сделать approve grants или отключить recovery.

## 11. Критерии

- UI и ИИ управляют одним состоянием плеера/устройства.
- Вклад третьей стороны виден в добавленной точке без правки core screen.
- Декларативная генерация включает все состояния, локали и accessibility.
- Новый компонент регистрируется плагином renderer, а не новой веткой core switch.
- Выключение плагина снимает route и не ломает back stack.
- Голосовой provider можно заменить целиком с сохранением семантики turn/error/cancel.
- Восстановление доступно при повреждении пользовательского UI.
